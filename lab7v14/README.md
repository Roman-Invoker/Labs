# Лабораторна робота №7: Узагальнені типи (Generics) та IRepository з where-обмеженнями

Цей репозиторій містить рішення для лабораторної роботи.

 Мета роботи

Навчитися створювати узагальнені інтерфейси та класи, застосовувати `where`-обмеження для типів-параметрів, а також розробляти модульні тести для перевірки коректності узагальнених реалізацій.

## Теоретичні відомості

* **Generics (Узагальнення):** Дозволяють створювати класи, інтерфейси та методи, які працюють з будь-яким типом даних, забезпечуючи безпеку типів (type safety) та високу продуктивність без зайвого боксингу.

* **`where`-обмеження:** Накладають обмеження на типи, які можуть передаватися як параметри (наприклад, `where T : class`, `where T : new()`, або обмеження через інтерфейси `where T : IEntity`).

* **Шаблон `IRepository`:** Поширений патерн проектування для абстрагування логіки доступу до даних.

* **Юніт-тестування:** Автоматизовані перевірки ізольованих частин коду для гарантування їх надійності та коректності бізнес-логіки.

##  Контрольні запитання

1. у Generics використовуються для накладання чітких умов на параметри типів. Вони дозволяють компілятору перевірити, чи має універсальний тип (Generic) необхідні властивості (наприклад, реалізує певний інтерфейс, успадковує клас або має конструктор без параметрів), перш ніж дозволити його використання.

* Обмеження інтерфейсу (Interface Constraint)
Найчастіший сценарій — коли нам потрібно, щоб тип реалізовував конкретний інтерфейс (наприклад, для порівняння або серіалізації).


* Обмеження конструктора (Constructor Constraint)
Якщо всередині універсального коду потрібно створити новий екземпляр типу через new T(), використовують обмеження new(). воно вимагає, щоб тип мав публічний конструктор без параметрів.

2. Шаблон IRepository — це архітектурний патерн, який використовується для ізоляції логіки роботи з даними від бізнес-логіки додатка. Простіше кажучи, він грає роль "посередника" або "прослойки" між вашим кодом та базою даних.
   Які переваги дає використання IRepository?
   * Розділення відповідальності (Separation of Concerns)
   * Легкість тестування (Mocking & Unit Testing)
   * Централізація логіки доступу до даних
   * Незалежність від технологій (Замінність)
   * Зменшення дублювання коду (DRY - Don't Repeat Yourself)

3. Юніт-тести є критично важливими при розробці узагальнених компонентів (generics / reusable components), оскільки такі компоненти створюються для повторного використання у багатьох різних частинах системи. Будь-яка помилка в узагальненому коді автоматично масштабується на всі місця, де він викликається.
Узагальнені компоненти працюють із типами, які на етапі написання коду часто невідомі. Тести допомагають перевірити поведінку компонента з різними категоріями даних.
Оскільки узагальнений компонент використовується у десятках або сотнях місць, його зміна — це завжди високий ризик
Для узагальнених компонентів складно написати вичерпну текстову документацію, яка б описувала всі нюанси роботи з різними типами.

4. Generics (узагальнення) вирішують три основні проблеми, які виникають при використанні типу object для створення універсального коду: безпека типів, продуктивність та читаність коду.
   Безпека типів (Type Safety) - Проблема з object: Компілятор дозволяє покласти в об'єкт будь-який тип даних. Помилки припускаються на етапі написання коду, але виявляються лише під час виконання програми (Runtime), що призводить до аварійного завершення (наприклад, InvalidCastException).

   Продуктивність - Проблема з object: Коли тип значення (наприклад, int, float, struct) приводиться до object, відбувається boxing (упаковка) — дані копіюються з оперативного стеку в купу (Heap).
