## 1. Приклади SRP

### 1.1. Вдале застосування SRP — `SqlMapper.TypeDeserializerCache` (Dapper)

- **Де видно:** окремий внутрішній клас у файлі `Dapper/SqlMapper.TypeDeserializerCache.cs`; у стек-трейсах (наприклад, issue [#2142](https://github.com/DapperLib/Dapper/issues/2142)) видно метод `TypeDeserializerCache.GetReader(...)`, який викликається з `SqlMapper.GetDeserializer(...)`.
- **Відповідальність:** лише кешування/видача десеріалізаторів для типу. Сама генерація десеріалізатора (IL) і виконання запитів — деінде.
- **Переваги/ризики:** політику кешу (структура ключа, очищення) можна змінювати, не чіпаючи виконання SQL; кеш тестується окремо. Ризик — додаткова зв'язність: `SqlMapper` викликає кеш (наприклад, `TypeDeserializerCache.Purge()` у `PurgeQueryCache`).
- **Нова функція:** зміна стратегії кешування (інший ключ чи інвалідація) торкається тільки цього класу.

### 1.2. Вдале застосування SRP — класи пайплайна MediatR (`MediatR.Pipeline`)

- **Де видно:** простір імен `MediatR.Pipeline` містить окремі behavior-класи: pre-processor, post-processor, exception-processor та exception-action-processor (чотири типи, що реалізують `IPipelineBehavior<TRequest, TResponse>`; перелік підтверджено структурним аналізом проєкту `src/MediatR/MediatR.csproj`, див. [огляд Metalama MCP](https://postsharp.net/blog/metalama-mcp-server)). Опис роботи — у [вікі: Behaviors](https://github.com/LuckyPennySoftware/MediatR/wiki/Behaviors).
- **Відповідальність:** кожен клас робить одну справу — запускає pre-, post-процесори або обробляє винятки; логіка самого запиту (handler) від них відокремлена.
- **Переваги/ризики:** кожну крос-катінг-задачу можна вмикати/вимикати окремою реєстрацією; код простий для тестування. Ризик — порядок реєстрації behavior-ів впливає на результат (наприклад, порядок `RequestExceptionActionProcessorBehavior` та `RequestExceptionProcessorBehavior` описано у вікі).
- **Нова функція:** щоб додати, наприклад, логування чи валідацію, пишемо новий behavior і не змінюємо наявні.

## 2. Приклади порушення SRP (Dapper, `Dapper/SqlMapper.cs`)

Файл у вибраному коміті має **3722 рядки** (~188 KB) і містить `public static partial class SqlMapper`.

### 2.1. Клас `SqlMapper` — «божественний» статичний клас (рівень класу)

- **Де видно:** в одному класі одночасно:
  1. **кеш запитів** — `_queryCache`, `SetQueryCache`, `CollectCacheGarbage`, `PurgeQueryCache`, `GetCachedSQL`, `GetHashCollissions`;
  2. **реєстр відповідності .NET-типів і `DbType`** — `typeMap`, статичний конструктор, `AddTypeMap`, `RemoveTypeMap`, `LookupDbType`;
  3. **реєстр обробників типів** — `typeHandlers`, `ResetTypeHandlers`, `AddTypeHandler`, `AddTypeHandlerImpl`;
  4. **публічний API виконання запитів** — `Execute`, `ExecuteScalar`, `ExecuteReader`, `Query`, `QueryFirst`, `QuerySingle`, `QueryMultiple` та їхні перевантаження;
  5. **внутрішня реалізація виконання** — `ExecuteImpl`, `QueryImpl`, `QueryRowImpl` тощо.
- **Це не лише «великий обсяг коду»:** тут різні *причини для змін* — зміна політики кешу, зміна мапінгу типів, зміна API виконання запитів змушують редагувати один і той самий клас. Розбиття на `partial`-файли (`SqlMapper.Async.cs`, `SqlMapper.TypeDeserializerCache.cs` тощо) лише розподіляє код по файлах, але не розділяє відповідальності.
- **Ризики:** високий поріг входу для контриб'юторів, складні зміни без побічних ефектів, статичний глобальний стан ускладнює тестування.
- **Нова функція:** будь-яка нова можливість (наприклад, додатковий тип параметрів) зачіпає великий спільний файл.

### 2.2. Метод `AddTypeHandlerImpl` — багато обов'язків в одному методі (рівень методу)

- **Де видно:** метод `SqlMapper.AddTypeHandlerImpl(Type type, ITypeHandler handler, bool clone)` самостійно:
  1. перевіряє аргументи;
  2. нормалізує тип (обробка `Nullable<T>` і value-типів);
  3. робить *clone-mutate-replace* словника `typeHandlers` для потокобезпеки;
  4. через рефлексію (`MakeGenericType(...).GetMethod(...).Invoke(...)`) оновлює статичний кеш `TypeHandlerCache<T>`;
  5. додає чи видаляє обробник (для `handler == null`) у словнику.
- **Ризики:** метод складно тестувати й змінювати: правка однієї частини (наприклад, логіки Nullable) може зламати іншу; рефлексія приховує помилки до часу виконання.
- **Нова функція:** щоб, скажімо, додати події при реєстрації обробника, доведеться втручатися в цей метод.

## 3. Приклади розширення за OCP

### 3.1. Dapper — `ITypeHandler` / `SqlMapper.AddTypeHandler<T>(TypeHandler<T>)`

- **Де видно:** у `SqlMapper.cs` — методи `AddTypeHandler(Type, ITypeHandler)`, `AddTypeHandler<T>(TypeHandler<T>)`; у `ResetTypeHandlers` через той самий механізм реєструються вбудовані обробники `DataTableHandler`, `XmlDocumentHandler`, `XDocumentHandler`, `XElementHandler`.
- **OCP:** щоб навчити Dapper новому типу (наприклад, JSON-колонці), розробник пише власний `TypeHandler<T>` і реєструє його; код `SqlMapper` не змінюється. Той факт, що навіть вбудовані типи підключені через цей самий механізм, підтверджує, що точка розширення справжня.
- **Ризики/переваги:** розширення безпечне для наявного коду, але реєстр є глобальним статичним станом — реєстрація впливає на весь застосунок.
- **Нова функція:** новий тип = новий клас-обробник + один виклик `AddTypeHandler`.

### 3.2. MediatR — `IPipelineBehavior<TRequest, TResponse>` та `INotificationPublisher`

- **Де видно:** [вікі: Behaviors](https://github.com/LuckyPennySoftware/MediatR/wiki/Behaviors) — поведінки реєструються через `services.AddMediatR(cfg => cfg.AddBehavior<...>())`, у тому числі як відкриті узагальнені типи; [вікі: Home](https://github.com/jbogard/mediatr/wiki) — з MediatR 12 є `INotificationPublisher` з методом `Publish(IEnumerable<NotificationHandlerExecutor>, INotification, CancellationToken)`, що дає змогу підставити власну стратегію публікації (паралельну, послідовну тощо) через `AddMediatR`.
- **OCP:** поведінку конвеєра (логування, валідація, кеш) і стратегію розсилання сповіщень розширюють новими класами, не змінюючи `Mediator`.
- **Ризики/переваги:** гнучкість; ризик — неочевидний порядок виконання behavior-ів і «магія» реєстрації через DI.
- **Нова функція:** додати, наприклад, вимір часу виконання — новий `TimingBehavior<,>` і один рядок реєстрації.

## 4. Висновки

У Dapper видно типовий шлях зростання бібліотеки: `SqlMapper` почав як невеликий клас, а потім став «місцем, куди додають усе», тому кеш, реєстри типів і API виконання зараз живуть разом. Водночас автори виділили окремі класи там, де відповідальність була очевидною (`TypeDeserializerCache`), і створили справжню точку розширення `ITypeHandler`, яка відповідає OCP. MediatR, навпаки, спроєктований навколо розширення: behavior-и та стратегії публікації змінюють поведінку без правки ядра, а чіткі маленькі класи пайплайна показують хорошу практику SRP. Практичний висновок: перевіряти SRP потрібно за *причинами для змін*, а не за кількістю рядків, а OCP — за наявністю реальних точок розширення, якими користується сам код бібліотеки. Обидва принципи корисні, доки не перетворюються на самоціль: зайві абстракції так само ускладнюють підтримку, як і «божественні» класи.

## 5. Пропозиція рефакторингу для найгіршого прикладу (`SqlMapper`)

**Проблема:** клас `SqlMapper` поєднує кеш запитів, реєстри типів/обробників і API виконання запитів.

**Пропозиція (без поломки публічного API):**

1. Винести кеш у окремий внутрішній клас `QueryCache` (`_queryCache`, `SetQueryCache`, `TryGetQueryCache`, `CollectCacheGarbage`, `Purge...`).
2. Винести реєстри в `DbTypeRegistry` (`typeMap`, `AddTypeMap`, `RemoveTypeMap`, `LookupDbType`) та `TypeHandlerRegistry` (`typeHandlers`, `AddTypeHandler...`); у `AddTypeHandlerImpl` виділити окремі приватні методи: `NormalizeType`, `UpdateHandlerCache`, `ReplaceHandlerMap`.
3. Залишити `SqlMapper` як тонкий фасад: публічні методи (`Query`, `Execute`, `AddTypeHandler`...) делегують новим класам, щоб не ламати бінарну сумісність для користувачів бібліотеки.

**Обґрунтування:** кожен клас матиме одну причину для змін; кеш і реєстри можна тестувати окремо; зростання файлу зупиниться. **Ризики:** потрібні регресійні тести та акуратне збереження потокобезпеки (патерн clone-mutate-replace); не варто одразу переходити від статичного стану до DI — це змінило б публічний API.

## Відповіді на контрольні запитання

**1. Як відрізнити окрему відповідальність від просто великого обсягу коду?**
Відповідальність — це *причина для змін*. Якщо клас доводиться редагувати з різних незалежних причин (інша політика кешу, інший формат даних, інший API), у нього кілька відповідальностей, навіть якщо він малий. Великий клас, усі зміни якого стосуються однієї теми, може не порушувати SRP.

**2. Які ознаки в коді підтверджують дотримання OCP?**
Є абстракції (інтерфейси, базові класи, делегати) та місця їх реєстрації; нова поведінка додається новим класом без правки наявного коду; відсутні довгі `switch/if` за типом; сама бібліотека використовує ці абстракції для вбудованої функціональності (як `ITypeHandler` у Dapper).

**3. Чому важливо дивитися не лише на інтерфейси, а й на місця розширення системи?**
Наявність інтерфейсу ще не означає, що систему можна розширювати: якщо реалізації жорстко створюються через `new` або вибираються `switch`-ом, точки розширення немає. Реальне OCP видно там, де нові реалізації підключаються (реєстрація в DI, реєстр обробників, конфігурація пайплайна).

**4. Які ризики виникають при рефакторингу «під патерн» без реальної потреби?**
Надмірна складність і абстракції без користі (over-engineering), більше класів і непрямих викликів, складніше навчання нових людей, ризик регресій та зниження продуктивності, а також «розмазування» простої логіки по кількох файлах.
