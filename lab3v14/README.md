# Лабораторна робота №3. Життєвий цикл об'єкта та керування ресурсами

**Дисципліна:** Об'єктно-орієнтоване програмування
**Варіант:** 14 — клас `HttpClient` (спрощений)
**Інструмент:** .NET SDK, C#

## Мета

Поглибити розуміння життєвого циклу об'єкта в C#, навчитися працювати з некерованими ресурсами, реалізувати інтерфейс `IDisposable` та патерн Dispose.

## Опис класу `HttpClient`

Клас імітує HTTP-клієнт. Роль «некерованого ресурсу» виконує відкрите з'єднання з сервером.

| Елемент | Призначення |
|---|---|
| `_baseUrl` (`string`) | Базова адреса сервера |
| `_isConnected` (`bool`) | Стан з'єднання («некерований ресурс») |
| `_disposed` (`bool`) | Захист від повторного звільнення |
| `HttpClient(string baseUrl)` | Конструктор, що «відкриває» з'єднання |
| `Get(string endpoint)` | Виконує запит, якщо з'єднання відкрите |
| `protected virtual Dispose(bool disposing)` | Основна логіка звільнення ресурсів |
| `Dispose()` | Публічне звільнення: `Dispose(true)` + `GC.SuppressFinalize(this)` |
| `~HttpClient()` | Деструктор, що викликає `Dispose(false)` |


## Сценарії в `Main`

1. **`using`** — `Dispose()` викликається автоматично при виході з блоку.
2. **Явний виклик `Dispose()`** — об'єкт створено без `using`, звільнення виконується вручну.
3. **Без `Dispose()`** — ресурс звільняє деструктор після `GC.Collect()` та `GC.WaitForPendingFinalizers()`.

## Висновок

У ході роботи реалізовано клас `HttpClient`, який імплементує `IDisposable` та повний патерн Dispose: конструктор, публічний `Dispose()`, захищений віртуальний `Dispose(bool disposing)` і деструктор. Було досліджено три способи завершення роботи з ресурсом.

| Сценарій | Коли звільняється ресурс | Надійність | Що викликається |
|---|---|---|---|
| `using` | Одразу після виходу з блоку, навіть при винятку | Висока | `Dispose()` → `Dispose(true)` |
| Явний `Dispose()` | У момент виклику | Середня: залежить від програміста, ресурс може лишитися захопленим при `return` чи винятку до цього рядка | `Dispose()` → `Dispose(true)` |
| Без `Dispose()` | Невідомо коли: після збирання сміття та роботи фіналізатора | Низька: момент недетермінований | `~HttpClient()` → `Dispose(false)` |

**Ключові спостереження:**

- `using` є найкращим способом керування ресурсами, оскільки компілятор перетворює його на `try/finally`, що гарантує виклик `Dispose()`.
- `GC.SuppressFinalize(this)` у `Dispose()` прибирає об'єкт із черги фіналізації: ресурс уже звільнено, тож повторна робота деструктора зайва, а сам об'єкт не затримується в пам'яті на додаткове покоління GC.
- Розділення на `Dispose(true)` і `Dispose(false)` необхідне, бо під час фіналізації керовані об'єкти-поля могли вже бути зібрані GC, тому деструктор звільняє лише некеровані ресурси.
- Прапорець `_disposed` робить повторний виклик `Dispose()` безпечним.
- Деструктор слід розглядати лише як резервний механізм на випадок, якщо `Dispose()` забули викликати, а не як основний спосіб звільнення ресурсів.
