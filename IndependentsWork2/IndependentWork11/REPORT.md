# Звіт до самостійної роботи №17

**Тема:** LINQ pipelines: ETL та аналітика

## 1. Модель і дані

- Сутності: `Sale (Id, ProductId, Quantity, SaleDate, CustomerId)`, `Product (Id, Name, Category, UnitPrice)`, `Customer (Id, Name, City)`.
- Дані генеруються `DataGenerator` з `Random(42)`: **60 товарів** у 6 категоріях, **80 клієнтів** у 8 містах, **1000 продажів** за період 01.01.2025 — 31.10.2026. Дані відтворювані: кожен запуск дає ті самі результати.
- ETL-інтерпретація: **Extract** — генерація/читання колекцій; **Transform** — LINQ-пайплайни (з'єднання, групування, обчислення); **Load** — вивід результату в консоль.

## 2. Опис пайплайнів

### Пайплайн 1. Найпопулярніші продукти за категоріями

- **Мета:** для кожної категорії знайти 3 товари з найбільшою кількістю проданих одиниць.
- **Кроки та оператори:**
  1. `GroupBy(ProductId)` + `Sum(Quantity)` — загальна кількість проданого по кожному товару;
  2. `Join` з каталогом — отримуємо назву та категорію;
  3. `GroupBy(Category)` — групуємо товари за категоріями;
  4. `OrderByDescending(Quantity).ThenBy(Name).Take(3)` — три лідери (за рівної кількості порядок визначає назва, тому результат стабільний);
  5. `OrderBy(Category)` — детермінований порядок категорій.
- **Чому так:** спершу агрегуємо продажі (1000 рядків -> ≤ 60), і лише потім з'єднуємо з каталогом, тобто `Join` працює з набагато меншою колекцією.

### Пайплайн 2. Дохід за містами клієнтів

- **Мета:** загальний дохід по місту клієнта, від більшого до меншого.
- **Оператори:** `Join(продажі, товари)` -> дохід рядка `Quantity * UnitPrice` -> `Join(клієнти)` -> `GroupBy(City)` -> `Sum(Revenue)` -> `OrderByDescending`.
- **Чому так:** ціна є лише в `Product`, а місто лише в `Customer`, тому потрібні два `Join`; дохід обчислюємо до групування, щоб `Sum` працював за простим полем.

### Пайплайн 3. Продажі за місяцями та роками

- **Мета:** кількість одиниць і дохід за кожним місяцем кожного року.
- **Оператори:** `Join(товари)` -> `GroupBy(new { Year, Month })` (складений ключ) -> `Sum(Quantity)`, `Sum(Revenue)` -> `OrderBy(Year).ThenBy(Month)`.
- **Чому так:** ключ групування — анонімний тип із двох полів; `ThenBy` гарантує хронологічний порядок (а не лексикографічний).

### Пайплайн 4 (додатковий). Топ-5 клієнтів і їхня улюблена категорія

- **Мета:** п'ятеро клієнтів із найбільшими витратами та категорія, у якій вони купили найбільше одиниць.
- **Оператори:** `Join(товари)` -> `GroupBy(CustomerId)` -> для кожного клієнта `Sum` витрат і **вкладений** `GroupBy(Category)` з вибором категорії з найбільшою кількістю -> `Join(клієнти)` -> `OrderByDescending(TotalSpent)` -> `Take(5)`.

## 3. Вимірювання продуктивності

Для кожного пайплайну створюється **новий** `Stopwatch`. Вимірюються два значення: **перший запуск** (включає JIT-компіляцію й «холодні» кеші) та **середнє за 200 повторних запусків** («гарячий» режим). Результат матеріалізується (`ToList`), тому вимірюється повне виконання запиту, а не лише побудова відкладеного запиту.

## 4. Аналіз результатів

1. **Перший запуск приблизно у 6–54 рази повільніший** за середній. Основна причина — JIT-компіляція: LINQ-методи й узагальнені типи компілюються при першому виклику. Саме тому перший замір не відображає реальну продуктивність запиту.
2. **Пайплайн 1 найдовше «прогрівався»** (10.8 мс), бо використовує найбільше різних операторів (два `GroupBy`, `Join`, `OrderBy`, `ThenBy`, `Take`), але в гарячому режимі він найшвидший (0.2 мс): спершу агрегація 1000 рядків до 60, а вже потім з'єднання.
3. **Пайплайн 4 найповільніший у гарячому режимі** (0.64 мс): вкладений `GroupBy` для кожного з 80 клієнтів, повторні агрегації `Sum` усередині `OrderByDescending`, два `Join`.
4. **Інші чинники впливу:** розмір вхідних даних, кількість проміжних колекцій і аллокацій (анонімні типи, ітератори, хеш-таблиці `Join`/`GroupBy`), робота збирача сміття, режим збирання (Debug повільніший за Release), фонове навантаження машини, точність `Stopwatch`.
5. **Обмеження вимірювань:** одна VM без ізоляції та без BenchmarkDotNet, тож абсолютні значення орієнтовні. Співвідношення «перший запуск ≫ середнє» стабільне.

## 5. Висновки

- LINQ добре підходить для ETL і аналітики в пам'яті: пайплайн з 4–7 операторів замінює десятки рядків циклів і тимчасових словників, а код читається як опис задачі.
- Порядок операторів впливає на ефективність: **спочатку скорочуємо дані (`Where`, агрегація), потім з'єднуємо й сортуємо**.
- Для тисяч рядків LINQ працює за долі мілісекунди. Для мільйонів рядків слід звертати увагу на аллокації, використовувати `Dictionary`-пошук замість повторних `Join`, а іноді переходити на PLINQ чи БД.
- Читабельність зберігається, коли кожен пайплайн винесено в окремий метод із промовистою назвою й документацією, а результат описаний типізованими `record`-ами.
