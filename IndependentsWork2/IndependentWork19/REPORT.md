# Звіт до самостійної роботи №19

**Тема:** Дизайн винятків і політики retry: теорія та кейси Polly

## 1. Власний тип винятку

`InsufficientFundsException : Exception` (предметна область — банківський рахунок):

- властивості `RequestedAmount` (запитана сума) і `CurrentBalance` (баланс) та похідна `Shortfall` (скільки не вистачає);
- три стандартні конструктори: `()`, `(string message)`, `(string message, Exception innerException)`, а також `(message, requestedAmount, currentBalance)` для контексту помилки;
- у `Main` показано `try / catch (InsufficientFundsException) / catch (Exception) / finally`: специфічний `catch` стоїть раніше за загальний, `finally` виконується завжди.

## 2. Сценарії Polly

Усі сценарії побудовано на актуальному API `ResiliencePipelineBuilder` (Polly 8.x) і логуються з часовими мітками (повний вивід у [README.md](README.md)).

### Сценарій 1. Зовнішній API тимчасово недоступний — Retry

- **Проблема:** сервіс погоди іноді повертає `503`, але за кілька сотень мілісекунд знову працює. Це тимчасовий збій.
- **Стратегія:** **Retry**, бо збій короткочасний і повторний виклик, імовірно, вдасться. `MaxRetryAttempts = 3`, `Delay = 200 мс`, `BackoffType = Exponential`, **`UseJitter = true`**. Експоненційна затримка дає сервісу час відновитися, jitter не допускає одночасних повторів багатьох клієнтів. Повторюються лише `HttpRequestException` (`ShouldHandle`).
- **Фрагмент коду:**

  ```csharp
  new ResiliencePipelineBuilder()
      .AddRetry(new RetryStrategyOptions
      {
          ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
          MaxRetryAttempts = 3,
          Delay = TimeSpan.FromMilliseconds(200),
          BackoffType = DelayBackoffType.Exponential,
          UseJitter = true,
          OnRetry = args => { /* лог спроби */ return default; }
      })
      .Build();
  ```

- **Вивід:** перші два виклики падають із `503`, між ними затримки 141 мс і 331 мс (зростають + випадкова складова), третя спроба успішна.

### Сценарій 2. База даних недоступна — Circuit Breaker

- **Проблема:** з'єднання з БД розірвано надовго. Якщо кожен запит і далі намагається дістатися БД (та ще й із повторами), ми марнуємо ресурси та додатково навантажуємо базу, яка намагається піднятися.
- **Стратегія:** **Circuit Breaker**: `FailureRatio = 0.5`, `MinimumThroughput = 3`, `SamplingDuration = 10 с`, `BreakDuration = 1 с`. Після трьох невдач автомат розмикається (Open): запити **миттєво відхиляються** з `BrokenCircuitException`, не звертаючись до БД. Через `BreakDuration` автомат переходить у Half-Open, пропускає пробний запит; якщо він успішний, автомат замикається (Closed).
- **Вивід:** запити 1–3 падають, на третьому автомат розмикається; запити 4–6 відхиляються миттєво (реальних звернень до БД лише 3); після очікування пробний запит №7 проходить, і автомат замикається, а №8 виконується нормально.
- **Чому не Retry:** повтори на «мертвому» сервісі лише збільшили б навантаження; автомат зупиняє потік запитів.

### Сценарій 3. Брокер повідомлень перевантажений — Timeout + Retry + Fallback

- **Проблема:** брокер відповідає надто повільно; без обмеження часу потік чекав би необмежено довго.
- **Стратегія (комбінація, порядок від зовнішньої до внутрішньої):**
  1. **Fallback** (зовнішня): якщо все не допомогло, зберегти повідомлення в локальну папку `outbox` (запасний варіант), тож повідомлення не втрачається.
  2. **Retry**: дві повторні спроби з експоненційною затримкою лише після `TimeoutRejectedException`.
  3. **Timeout** (внутрішня): кожна спроба обмежена 300 мс; після перевищення спроба скасовується через `CancellationToken`.
- **Вивід:**
  - *3а:* перші дві спроби скасовано за тайм-аутом (по ≈ 300 мс), після двох повторів третя швидка й успішна;
  - *3б:* усі три спроби перевищують тайм-аут, повтори вичерпано, спрацьовує Fallback і повідомлення зберігається в `outbox`.

## 3. Коли кидати виняток, а коли повертати `Result<T>`

Виняток доречний, коли метод **не може виконати свій контракт** через справді виняткову ситуацію: розірване з'єднання, файл не знайдено, на рахунку недостатньо коштів. Він містить стек викликів і його неможливо «випадково» проігнорувати, але розкрутка стека дорожча, а порожній `catch` може приховати помилку. `Result<T>` (або `bool`/`null`) краще для **очікуваних** невдач, які трапляються в нормальному потоці: валідація введення, пошук елемента, що може не існувати. Він швидший, а можливість невдачі видно прямо в сигнатурі. Мінус: результат легко не перевірити. У коді це показано на різниці між `BankAccount.Withdraw` (виняток) і `BankAccount.ParseAmount` (`Result<decimal>`).

## 4. Загальні висновки щодо Polly

**Переваги:**

- Готові перевірені стратегії (Retry, Circuit Breaker, Timeout, Fallback, Hedging, Rate Limiter) замість власних реалізацій, у яких легко помилитися.
- Декларативна композиція в одному `ResiliencePipeline`; порядок стратегій керує поведінкою.
- Гнучка конфігурація (backoff, jitter, предикати `ShouldHandle`) і зручні події для логування й телеметрії (`OnRetry`, `OnOpened`, `OnTimeout`, ...).
- Однаково працює для синхронного та асинхронного коду.

**Обмеження й ризики:**

- Додаткова залежність і крива навчання; порядок стратегій у пайплайні неочевидний (Timeout усередині Retry, а не навпаки).
- Retry **небезпечний для неідемпотентних операцій** (подвійне списання), тому потрібні ключі ідемпотентності.
- Невдалі параметри (забагато повторів, довгі затримки) загальмують систему або створять «шторм» запитів; кожну стратегію треба налаштовувати під конкретний сервіс.
- Polly не виправляє причину збою: він лише згладжує тимчасові проблеми. Постійні помилки (некоректні дані, `401`, `404`) повторювати не варто.
- Синхронні пайплайни блокують потік під час очікування (`Thread.Sleep`-подібні затримки); у серверному коді краще використовувати `ExecuteAsync`.
