# Звіт до самостійної роботи №18

**Тема:** PLINQ: дослідження продуктивності та безпеки

## 1. Експерименти з продуктивності

**Дані:** `List<int>` із 1 000 000, 5 000 000 та 10 000 000 випадкових чисел із діапазону [2; 200 000] (`Random(42)`).
**Операція:** `Where(IsPrime).Select(n => Math.Sqrt(n)).ToList()`, де `IsPrime` — пробне ділення до √n (відносно дорога операція, тож накладні витрати на паралелізм можуть окупитися).
**Вимірювання:** `Stopwatch`, один запуск кожного варіанта після прогріву JIT; три варіанти: LINQ, PLINQ (`AsParallel()`), PLINQ з `AsOrdered()`.

## 2. Аналіз: коли PLINQ швидший, а коли ні

- **У наведених вимірюваннях PLINQ не виграв** (прискорення 0.7–0.9× у більшості випадків). Причина проста: середовище має **один логічний процесор**. PLINQ не може виконувати роботу одночасно, але платить за розбиття даних на частини, координацію потоків і злиття результатів. Це чиста накладна витрата.
- **Розкид між запусками.** Варіант `AsOrdered` на 5 млн дав 1.18×, хоча логічно не може бути швидшим за звичайний PLINQ. Це шум вимірювання: JIT, збирач сміття при створенні великих списків, одноразові виміри, спільна VM. Для достовірності потрібні повторні запуски та BenchmarkDotNet, тому окремі числа не слід вважати точними.
- **На багатоядерному процесорі** для такої CPU-bound-операції очікується прискорення, близьке до кількості ядер (на практиці менше через розбиття, злиття й `ToList`). Виграш зростає із розміром даних і вартістю операції на елемент.
- **PLINQ невигідний,** коли: операція на елемент дешева (накладні витрати більші за користь), колекція мала, запит вимагає збереження порядку (`AsOrdered` додає буферизацію), потрібне послідовне джерело з повільним доступом, операція упирається у вводу-виводу, а не в процесор.
- **Висновок із вимірювань:** тому й порівнюють кілька розмірів: у різних режимах співвідношення різне, а один замір легко вводить в оману.

## 3. Сценарій із побічними ефектами

**Умова:** порахувати кількість чисел, кратних 7, серед 5 000 000 елементів. Еталонний результат (послідовно, без побічних ефектів): **713 544**. Для PLINQ задано `WithDegreeOfParallelism(4)`, щоб потоки працювали паралельно, навіть якщо ядро одне.

### Проблема 1. Спільний лічильник без синхронізації

```csharp
int counter = 0;
data.AsParallel().ForAll(n => { if (n % 7 == 0) counter++; });
```

`counter++` — це три кроки: прочитати, збільшити, записати. Два потоки можуть прочитати те саме значення й обидва записати «значення + 1», тобто один приріст губиться. На багатоядерній машині втрати зазвичай видно одразу. На одноядерному середовищі вікно гонки дуже вузьке (див. вивід: втрат 0). Щоб показати проблему й там, між читанням і записом додано `Thread.Yield()`: тоді лічильник показує 35–44 тисячі замість 71 131 (втрачено ≈ 27–35 тисяч, **близько половини**). Результат також **нестабільний** між запусками.

### Проблема 2. `List<T>.Add` з кількох потоків

`List<T>` не потокобезпечний: два потоки можуть одночасно записати в той самий індекс або одночасно змінити внутрішній масив. У п'яти спробах результат був правильним лише двічі, інакше в списку було 661 403, 697 654 або 460 396 елементів замість 713 544. Можливі й винятки (`IndexOutOfRangeException`, `ArgumentException`).

### Виправлення

| Спосіб | Результат | Коментар |
|---|---|---|
| `lock (sync) { counter++; }` | 713 544, 52 мс | Правильно; потоки чекають одне одного на блокуванні. |
| `Interlocked.Increment(ref counter)` | 713 544, 40 мс | Правильно, швидше за `lock`: атомарна операція процесора без блокування. Найкращий варіант для лічильника. |
| `ConcurrentBag<int>.Add` | 713 544, 76 мс | Правильно; потокобезпечна колекція, підходить, коли потрібні самі елементи, а не лише кількість. |
| `AsParallel().Count(...)` | 713 544, 51 мс | Найкраще за дизайном: **без побічних ефектів**, PLINQ сам зливає часткові результати. |

## 4. Висновки

1. PLINQ — не «прискорювач за замовчуванням». Він має сенс для **CPU-bound** операцій над великими даними на **багатоядерному** процесорі; обов'язково вимірюйте на реальних даних і кількох розмірах колекції.
2. На одному ядрі або з дешевою операцією PLINQ може бути **повільнішим** за LINQ через накладні витрати на паралелізм.
3. Запит PLINQ не повинен мати побічних ефектів. Зміна спільного стану без синхронізації дає **тихі, нестабільні й важко відтворювані помилки** (втрачені оновлення, пошкоджені колекції).
4. Безпечні підходи: віддавати результат через оператори PLINQ (`Count`, `Sum`, `Aggregate`, `ToList`), а якщо спільний стан неминучий — `Interlocked`, `lock` або `ConcurrentBag`/`ConcurrentDictionary`.
5. Розуміння механізму (розбиття на частини, злиття, порядок, потокобезпечність) важливіше за сам виклик `AsParallel()`.
