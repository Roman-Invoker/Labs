## 2. Пайплайни

Усі пайплайни завершуються `ToList()`, тому вимірювання охоплює реальне виконання.

### Пайплайн 1. Топ-3 товари за категоріями

**Задача:** для кожної категорії знайти три товари з найбільшою сумарною кількістю проданих одиниць.

```csharp
sales
    .GroupBy(s => s.ProductId)
    .Select(g => new { ProductId = g.Key, TotalQuantity = g.Sum(s => s.Quantity) })
    .Join(products, sold => sold.ProductId, p => p.Id,
          (sold, p) => new { p.Name, p.Category, sold.TotalQuantity })
    .GroupBy(x => x.Category)
    .Select(g => new CategoryTop(g.Key,
        g.OrderByDescending(x => x.TotalQuantity)
         .ThenBy(x => x.Name, StringComparer.Ordinal)
         .Take(3)
         .Select(x => new ProductQuantity(x.Name, x.TotalQuantity)).ToList()))
    .OrderBy(c => c.Category, StringComparer.Ordinal)
    .ToList();
```

| Оператор | Навіщо |
|----------|--------|
| `GroupBy` за `ProductId` + `Sum` | згортає тисячі продажів у одну суму на товар |
| `Join` з товарами | додає назву й категорію (їх немає в `Sale`) |
| `GroupBy` за категорією | групує товари для топ-списків |
| `OrderByDescending` + `ThenBy` + `Take` | сортує за кількістю; `ThenBy` за назвою робить порядок однаковим навіть за рівної кількості |

### Пайплайн 2. Дохід за містами клієнтів

**Задача:** загальний дохід і кількість продажів для кожного міста.

```csharp
sales
    .Join(products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.CustomerId, Revenue = s.Quantity * p.UnitPrice })
    .Join(customers, x => x.CustomerId, c => c.Id,
          (x, c) => new { c.City, x.Revenue })
    .GroupBy(x => x.City)
    .Select(g => new CityRevenue(g.Key, g.Sum(x => x.Revenue), g.Count()))
    .OrderByDescending(r => r.Revenue)
    .ThenBy(r => r.City, StringComparer.Ordinal)
    .ToList();
```

Дві сполуки `Join` послідовно приєднують ціну товару, а потім місто клієнта. Дохід (`Quantity * UnitPrice`) обчислюється на першому кроці, щоб не повертатися до товарів після групування.

### Пайплайн 3. Продажі за місяцями й роками

**Задача:** кількість проданих одиниць і дохід у розрізі кожного місяця.

```csharp
sales
    .Join(products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.SaleDate, s.Quantity, Revenue = s.Quantity * p.UnitPrice })
    .GroupBy(x => new { x.SaleDate.Year, x.SaleDate.Month })
    .Select(g => new MonthlySales(g.Key.Year, g.Key.Month,
                                  g.Sum(x => x.Quantity), g.Sum(x => x.Revenue)))
    .OrderBy(m => m.Year).ThenBy(m => m.Month)
    .ToList();
```

`GroupBy` використовує **складений ключ** `{ Year, Month }`: анонімні типи в C# мають порівняння за значенням, тому два однакові ключі потрапляють в одну групу. Без року продажі січня 2024 і січня 2025 злилися б.

### Пайплайн 4 (власний). Топ-5 клієнтів з улюбленою категорією

**Задача:** п'ять клієнтів, які витратили найбільше, із сумою, кількістю замовлень і **категорією, у якій вони купили найбільше одиниць**.

```csharp
sales
    .Join(products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.CustomerId, p.Category, s.Quantity, Revenue = s.Quantity * p.UnitPrice })
    .GroupBy(x => x.CustomerId)
    .Select(g => new
    {
        CustomerId = g.Key,
        Total = g.Sum(x => x.Revenue),
        Orders = g.Count(),
        FavoriteCategory = g.GroupBy(x => x.Category)
                            .OrderByDescending(cg => cg.Sum(x => x.Quantity))
                            .ThenBy(cg => cg.Key, StringComparer.Ordinal)
                            .First().Key
    })
    .OrderByDescending(x => x.Total).ThenBy(x => x.CustomerId)
    .Take(5)
    .Join(customers, x => x.CustomerId, c => c.Id,
          (x, c) => new TopCustomer(c.Name, c.City, x.Total, x.Orders, x.FavoriteCategory))
    .ToList();
```

Особливості:

- **Вкладений `GroupBy`** у `Select` знаходить улюблену категорію кожного клієнта (категорія з найбільшою сумарною кількістю).
- **`Take(5)` стоїть перед фінальним `Join`**: імена й міста підтягуються лише для п'яти клієнтів, а не для всіх 80. `Enumerable.Join` зберігає порядок зовнішньої послідовності, тому порядок топ-5 не змінюється.

### Додатково: пайплайн 2 без LINQ

`RevenueByCityManual` робить те саме двома словниками (`priceById`, `cityById`) і одним циклом по продажах. Результат збігається з LINQ-версією (це перевіряється під час вимірювань). Він потрібен для відповіді на питання, скільки «коштує» зручність LINQ.

## 4. Аналіз продуктивності

### Що впливає на швидкість пайплайнів

1. **Перший запуск проти повторних.** Перший виклик включає JIT-компіляцію методів LINQ та лямбд, тому суттєво повільніший за наступні. Саме тому в таблиці є обидва показники. У моїх вимірах перший запуск повільніший у `[...]` разів.
2. **Обсяг даних.** Кожен пайплайн проходить усі продажі принаймні раз, тому час зростає приблизно пропорційно N. Сортування (`OrderBy`) дає внесок O(m log m), але сортуються вже згруповані дані (60 товарів, 8 міст, 24 місяці, 80 клієнтів), тому він малий порівняно з основним проходом. У моїх вимірах під час збільшення N у 1000 разів (з 1000 до 1 000 000) час пайплайну 2 зріс у `[...]` разів.
3. **`Join` будує хеш-таблицю.** `Enumerable.Join` для кожного виклику будує пошукову структуру за внутрішньою послідовністю (товари, клієнти), а потім потоково проходить зовнішню. Тому два `Join` у пайплайні 2 коштують більше, ніж один у пайплайні 3.
4. **`GroupBy` буферизує дані.** Він збирає всі елементи в групи, перш ніж віддати перший результат, і виділяє пам'ять під групи. Вкладений `GroupBy` у пайплайні 4 створює додаткові групи для кожного з 80 клієнтів, тож цей пайплайн має найбільшу кількість виділень пам'яті.
5. **Проміжні об'єкти.** Анонімні типи, делегати (лямбди) та проміжні послідовності створюють об'єкти в купі, що збільшує навантаження на збирач сміття (GC), особливо на мільйоні продажів.
6. **Арифметика `decimal`.** Дохід рахується в `decimal` (точно для грошей), але ця арифметика повільніша за `int`/`double`.
7. **Порядок операторів.** У пайплайні 4 `Take(5)` стоїть перед фінальним `Join`, тому приєднання клієнтів виконується для п'яти записів, а не для 80. Фільтрувати й обмежувати дані варто якомога раніше.
8. **Матеріалізація.** Відкладене виконання LINQ означає, що без `ToList()` вимірювався б лише час створення запиту (близько нуля). Тому кожен пайплайн завершується `ToList()`.

### LINQ проти циклів (пайплайн 2)

Версія на циклах використовує два словники й один прохід, без проміжних послідовностей, анонімних типів та делегатів на кожен елемент. У моїх вимірах на 1 000 000 продажів LINQ-версія працює за `[...]` мс, а версія на циклах за `[...]` мс (у `[...]` разів швидше / повільніше). Результати обох версій збігаються.

## 5. Висновки

1. Складні задачі аналізу (кілька з'єднань, групувань і сортувань) у LINQ вмістилися в **декілька десятків рядків** і читаються як опис задачі: «згрупуй, приєднай, відсортуй, візьми перші». Версія на циклах пайплайну 2 довша, містить явні словники й ручне сортування, і її легше зіпсувати.
2. LINQ має **накладні витрати**: делегати, проміжні об'єкти, буферизація в `GroupBy`/`OrderBy`. Версія на циклах для того самого завдання швидша `[...]` (див. розділ 4), але ціна цього: більше коду та ризик помилок.
3. Продуктивність залежить від **порядку операторів**: раннє `Take`/`Where` скорочує обсяг даних для наступних кроків (пайплайн 4), а сортування й групування повторно використовуються з малою кількістю груп.
4. **Висновок про ефективність LINQ для ETL:** для звичайних аналітичних задач на сотнях тисяч записів LINQ достатньо швидкий і значно зручніший; виграш у швидкості від ручних циклів потрібен лише в гарячих ділянках, де вимірювання показали проблему. Спершу пишіть читабельно на LINQ, потім вимірюйте, і лише тоді оптимізуйте (наприклад, замінюйте окремий пайплайн циклом чи Dictionary).
5. Для дуже великих обсягів можна розглянути паралельну обробку (PLINQ) або виконання запиту в базі даних, але для цього потрібні окремі вимірювання (див. самостійну №12).
